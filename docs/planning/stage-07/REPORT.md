# Этап 07 · Жизненный цикл Desktop Local

Ветка `stage-07-sqlite-first-run`, база `24d29ee9b84ed1d22fd303e2214bd85c9a4be5c6`.
Опубликованная миграция `0001` используется для SQLite и PostgreSQL.

## Первый и повторный запуск

1. Команда `python -m chimera run` проверяет настройки Desktop Local и
   берёт блокировки ОС для каталога профиля и файла SQLite. Блокировки
   действуют до закрытия сервера и Engine. На Windows используется
   блокировка диапазона файла. При аварии ОС освобождает дескрипторы.
2. В новом профиле создаются ключ подписи, исходный ключ Fernet,
   `chimera.db`, `uploads` и `backups`. В Windows каталог по умолчанию
   находится в `%LOCALAPPDATA%/Chimera`. Каждый новый ключ сначала
   записывается и сбрасывается на диск во временном каталоге внутри
   профиля, затем публикуется эксклюзивно.
3. SQLite включает WAL, `synchronous=NORMAL`, внешние ключи и ожидание
   блокировки до пяти секунд. Подготовка проверяет целостность и точную
   ревизию. SQLite DDL выполняется в явной транзакции. Маркер схемы
   создаётся после успешной миграции. При обновлении известной ревизии
   сначала создаётся полная проверенная копия. Ошибка копии прерывает
   обновление.
4. Пока в профиле нет пользователей, запускается настройка администратора.
   Flask слушает `127.0.0.1`; браузер получает секрет запуска через
   фрагмент URL и удаляет фрагмент из адресной строки. Форма требует
   loopback, ожидаемые Host и Origin, CSRF и секрет запуска. Сервер
   проверяет пароль по действующей политике. Организация, пользователь,
   роль и аудит записываются одной транзакцией. После фиксации открывается
   штатный вход. Для заранее заданного `ADMIN_DEFAULT_PASSWORD` действует
   прежняя процедура bootstrap со сменой пароля при входе.
5. Следующий запуск использует прежние файлы, пароли, роли и ревизию.
   Профиль с готовой схемой предлагает настройку, если в нём нет
   пользователей и записи о завершении настройки. Запись аудита
   сохраняется после удаления последней учётной записи и закрывает мастер.
   Если исходный ключ, ранее созданная база или поддерживаемая ревизия
   отсутствуют, запуск останавливается. Для прежнего `instance` укажите
   явный `CHIMERA_DATA_DIR` и верните оригинальные ключи.

## Резервирование и восстановление

Веб-раздел системного администратора использует SQLite Backup API из
отдельного соединения только для чтения. `VACUUM INTO` также создаёт
транзакционно согласованную БД, но Backup API позволяет копировать
страницами и ограничить ожидание. Снимок содержит зафиксированные данные
из WAL. Приложение проверяет свободное место, `integrity_check` и
`foreign_key_check`, затем публикует файл без замены существующего.
Соединения закрываются до публикации. Резервирование Server использует
`pg_dump`.

Команда `backup-profile` берёт блокировку остановленного Desktop Local
и создаёт в каталоге копий отдельный каталог с SQLite, `uploads`, ключами
подписи и шифрования, настройкой ключа слепого индекса и манифестом версии,
ревизии и SHA-256 файлов. Cookie, настройки темы и панели относятся к
профилю браузера. Эксплуатационные параметры, заданные через окружение,
нужно задать отдельно для проверочного запуска. Полные копии содержат
ключи и пользовательские данные. Windows создаёт каталог до записи
секретов с защищённой DACL для владельца, SYSTEM и локальных
администраторов. Том должен поддерживать постоянные ACL. Для внешнего
хранения применяйте защищённое хранилище. Срок хранения полных копий
задаёт владелец.

`restore-profile ИСТОЧНИК НАЗНАЧЕНИЕ --confirm` требует новый каталог
вне рабочего профиля, копии, загрузок и настроенной SQLite. Команда
отклоняет ссылки, junction и жёсткие ссылки в дереве файлов и проверяет
состав, хеши, ключи, обязательные таблицы, ревизию и целостность БД
в закрытом временном каталоге рядом с назначением. Имена из манифеста
используются для сравнения, пути записи берутся из проверенного дерева
файлов. Перед публикацией повторно проверяются назначение и идентичность
его родительских каталогов. Проверенный профиль публикуется
переименованием. После прерывания возможен закрытый временный каталог
без опубликованного результата. Манифест обнаруживает повреждение.
Подлинность копии зависит от доверенного хранилища.

## Ручная приёмка Windows

1. В новой PowerShell-сессии укажите `CHIMERA_MODE=desktop-local` и
   `CHIMERA_DATA_DIR` нового синтетического профиля в личном каталоге.
   Запустите `python -m chimera run`. Задайте и подтвердите пароль в
   открывшемся браузере, затем войдите.
2. Измените пароль и добавьте тестовое подразделение. Поместите
   синтетический файл в `uploads`. Создайте копию базы в интерфейсе.
3. Во второй сессии с тем же профилем запустите `run` и проверьте отказ.
   Остановите первый процесс, запустите его снова и войдите с изменённым
   паролем. Проверьте подразделение и файлы.
4. Остановите приложение и выполните `python -m chimera backup-profile`.
   Выполните восстановление в новый соседний каталог с `--confirm`.
   Укажите путь проверочного профиля в отдельной сессии PowerShell,
   используйте InPrivate и проверьте вход, данные и вложение.
5. Проверьте, что команда отклоняет существующий проверочный каталог
   и рабочий профиль. Вернитесь к исходной конфигурации и проверьте вход.

## Откат

Остановите Desktop Local и сохраните рабочий профиль, ключи и копии.
Проверьте в отдельном каталоге полную копию, сделанную до обновления.
Для отката на совместимую версию используйте предыдущий wheel и
проверенный профиль совместимой ревизии. При необходимости явно укажите
его через `CHIMERA_DATA_DIR` в отдельной сессии. Сохраните оба профиля
до приёмки. Для этой реализации ревизия остаётся `0001`.

## Замечания при приёмке

- **P2, исправлено.** После ошибки ввода общая логика форм подменяла узел
  формы, и кнопка оставалась выключенной. Исправленная форма сохраняет
  доступ только при проверенном токене и восстанавливает фокус.
- **P2, исправлено.** Первоначальная проверка Host отвергала
  `localhost` и нарушала вход на изолированном тестовом стенде.
  Штатный интерфейс принимает локальный адрес, а настройка
  администратора проверяет точный адрес, выданный при запуске.
- **P2, исправлено при финальном аудите.** Пустая таблица пользователей
  могла снова открыть мастер. Запись о создании администратора в той же
  транзакции теперь используется и при перезапуске, и при bootstrap.
- **P2, исправлено при финальном аудите.** Полная копия могла унаследовать
  широкие права родителя. Временный и опубликованный каталоги защищены
  собственной DACL, а на томе без постоянных ACL операция отклоняется.
- **P2, исправлено при финальном аудите.** Перед публикацией восстановления
  выполнялась только ранняя проверка пути. Добавлены повторная проверка
  назначения и идентичности каталогов, отказ на жёстких ссылках и отказ
  для SQLite с формально подходящей ревизией, но без обязательных таблиц.
- **P3, ограничение.** Последняя проверка и системное переименование
  выполняются отдельными вызовами. Родитель назначения, родитель копии
  и их предки должны быть доступны для изменения только доверенным
  пользователям. ACL самой копии защищает чтение, а право `DELETE_CHILD`
  родителя может разрешить перемещение каталога. Блокировка профиля
  координирует процессы штатного CLI Chimera. Прямое редактирование
  SQLite и вложений сторонними процессами требует остановки таких процессов.
  Рабочий профиль и отдельные веб-копии SQLite используют ACL своих
  настроенных каталогов.
  [Права и перемещение файлов в Windows](https://learn.microsoft.com/windows/win32/api/winbase/nf-winbase-movefileexa)

**NOT TESTED** — PyInstaller, Windows EXE и установщик, автоматическое
открытие браузера по умолчанию через системную ассоциацию, физическое
исчерпание места и отказ питания. HTTP-проверка
установленного пакета перехватывает URL от системного запуска браузера.

## Контроль перед публикацией

- SQLite-пути нормализуются в `core/config.py`; `run`, `migrate`,
  `bootstrap`, `status` и `backup-profile` используют блокировки
  профиля и SQLite. `status` открывает SQLite через общий движок,
  который настраивает WAL. Дополнительно отклоняется SQLite с жёсткой
  ссылкой: другое имя могло бы получить собственную блокировку и WAL.
  Доступ к изменению файлов и предков рабочего профиля остаётся доверенным.
- Дубли ключей JSON и путей манифеста отклоняются при декодировании.
  Файлы копируются по реальным именам, с эксклюзивным созданием
  в закрытом промежуточном каталоге; совпадение манифеста с фактическим
  набором файлов и SHA-256 обязательно.
- Общий pytest запускает регрессии профиля на Windows и Linux, а тест
  DACL выполняется на Windows. В Windows CI добавлен smoke первого
  запуска в предустановленном Edge.
  [Состав образа Windows Server 2025](https://github.com/actions/runner-images/blob/main/images/windows/Windows2025-Readme.md)
- `prepare_local_schema` вызывает `copy_profile` до `upgrade_head`,
  если существующая база находится на поддерживаемой ревизии, отличной
  от head. Тест `test_existing_schema_is_backed_up_before_upgrade`
  моделирует следующую ревизию и проверяет прекращение обновления при
  отказе копирования. Реального перехода на следующую ревизию пока нет.
  Ревизия `0001` сохранена.

На Windows отдельный прогон подтвердил, что путь через junction
