# Изолированные стенды Chimera

Команды выполняются из корня checkout на ветке этапа 02. Утилита использует исходники
Chimera, штатные миграции Alembic и штатную функцию bootstrap. У каждого стенда
свои тестовые ключи сессии и шифрования, БД, каталоги загрузок и копий.
Для запуска выберите рабочую копию, доступную на запись только вашему пользователю.

| Стенд | Режим | Приложение | База |
|---|---|---|---|
| Windows Local | `desktop-local` | `http://127.0.0.1:5801` | `.chimera-test-envs/sqlite/chimera.db` |
| Server в Linux VM | `server` | `http://127.0.0.1:5802` | PostgreSQL 16 на `127.0.0.1:55432`, БД `chimera_stage02`, кластер `.chimera-test-envs/postgres/pgdata` |

Оба адреса предназначены для локальной DEV-проверки через HTTP. Для Server выбран
выделенный кластер в Linux VM. Если браузер находится на хосте, откройте SSH-туннель
`ssh -N -L 127.0.0.1:5802:127.0.0.1:5802 <пользователь>@<vm>` и перейдите по тому же
адресу. Для проверки в браузере используйте отдельные профили или приватные окна
по очереди. Cookies для одного имени хоста общие между портами.

## Windows 10/11 · SQLite

Установите Python 3.11 и выполните в PowerShell:

```powershell
py -3.11 -m venv .venv-stage02
$py = ".\.venv-stage02\Scripts\python.exe"
& $py -m pip install -r requirements-dev.txt
& $py -m scripts.dev_test_env sqlite prepare
& $py -m scripts.dev_test_env sqlite status
& $py -m scripts.dev_test_env sqlite run
```

Остановите Flask через Ctrl+C. `run` также выполняет подготовку, поэтому для
ежедневной работы достаточно этой команды.

## Linux VM · PostgreSQL 16

Установите Python 3.11+ с модулем `venv` и серверные утилиты PostgreSQL 16.
На Debian/Ubuntu с настроенным репозиторием, содержащим пакет, это
`sudo apt install postgresql-16 python3-venv`. Держите порты 55432 и 5802 свободными.
Запускайте стенд из обычной учётной записи. `initdb` создаёт отдельный кластер
со SCRAM-аутентификацией и случайным ключом. [Установка PostgreSQL](https://www.postgresql.org/download/linux/)

```bash
export PATH="/usr/lib/postgresql/16/bin:$PATH"  # Debian/Ubuntu, иначе путь к bin PostgreSQL 16
python3 -m venv .venv-stage02
py=.venv-stage02/bin/python
"$py" -m pip install -r requirements-dev.txt
"$py" -m scripts.dev_test_env postgres prepare
"$py" -m scripts.dev_test_env postgres status
"$py" -m scripts.dev_test_env postgres run
```

После Ctrl+C PostgreSQL продолжает работать, чтобы выполнить `status` или снова
запустить приложение. Для остановки кластера выполните
`"$py" -m scripts.dev_test_env postgres stop`. Следующий `prepare` или `run`
откроет ту же БД. При проблеме запуска проверьте наличие бинарников
`initdb --version` и `pg_ctl --version`, свободные порты и тестовый журнал
`.chimera-test-envs/postgres/postgres.log`. Если процесс не запустился,
`status` завершится с ненулевым кодом. [Управление кластером через pg_ctl](https://www.postgresql.org/docs/16/app-pg-ctl.html)

## Синтетические учётные записи

Для нового стенда `prepare` генерирует случайный начальный пароль для всех
синтетических учёток. Для SQLite его можно прочитать командой
`Get-Content -LiteralPath .chimera-test-envs/sqlite/fixture_password.key`.
Для Server файл находится в `.chimera-test-envs/postgres/fixture_password.key` внутри VM.
При первом входе `admin` смените пароль. Повторная подготовка сохраняет пароли
действующих учёток, в том числе в стендах, созданных до введения генерации.

| Логин | Роль | Организация |
|---|---|---|
| `admin` | Администратор системы, член колледжа | Учебный колледж «Пример» |
| `head` | Руководитель | Учебный колледж «Пример» |
| `curator1` | Куратор | Учебный колледж «Пример» |
| `curator2` | Куратор | Учебный университет «Образец» |
| `viewer` | Наблюдатель | Учебный университет «Образец» |

## Ручная приёмка

1. Выполните `prepare` и `status` для обоих стендов. Сверьте режим, СУБД и
   равенство ревизий Alembic (на этапе 02 обе `0001`). Для Server проверьте,
   что диагностика показывает PostgreSQL 16.
2. Откройте `run` и войдите под `admin`. После смены пароля откройте
   административную часть, проверьте две организации и пять пользователей.
3. Измените тестовое имя куратора. Остановите приложение и PostgreSQL, где
   применимо. Снова выполните `prepare`, `status` и `run`. Войдите с новым
   паролем администратора и убедитесь, что имя, пользователи и организации сохранились.
4. Остановите приложение. Запустите `clean` без `--confirm` и проверьте,
   что команда вернула ошибку, а стенд сохранился. Для добровольного сброса
   выполните подтверждённую очистку ниже. Повторите `prepare` и проверьте
   исходные синтетические записи. При наличии второго стенда проверьте, что
   его данные сохранились.

## Очистка и автоматизированные проверки

```powershell
& $py -m scripts.dev_test_env sqlite clean --confirm
Remove-Item Env:CHIMERA_TEST_DATABASE_URL -ErrorAction SilentlyContinue
& $py -B -m pytest -q
```

```bash
"$py" -m scripts.dev_test_env postgres clean --confirm
unset CHIMERA_TEST_DATABASE_URL
CHIMERA_STAGE02_TEST_POSTGRES=1 "$py" -B -m pytest -q tests/test_dev_test_env.py
```

Освободите порт 55432 перед интеграционным тестом. Он создаёт кластер внутри
временного каталога pytest. `CHIMERA_TEST_DATABASE_URL` относится к старой
тестовой оснастке, которая удаляет таблицы в переданной ей базе. Для проверок
этапа 02 оставьте её незаданной.

Для каждой операции путь вычисляется из расположения исходников и имени
стенда. Очистка проверяет соответствующий пути маркер владения и проверяет дерево
на ссылки, junction, специальные файлы и точки монтирования. Очистка Server
останавливает только выделенный кластер. Для запущенного кластера сверяются
реальный каталог данных и major-версия через фиксированное loopback-подключение.
После остановки удаляется каталог стенда. Соединение для остановки не изменяет
SQL-данные. Значения из `.env`, `DATABASE_URL`, `CHIMERA_DATA_DIR`, `APP_HOST`
и переменных libpq не задают цель очистки или миграций.

Если предыдущий процесс был принудительно прерван и осталась блокировка,
сначала убедитесь, что с этим стендом не работает другой процесс. Затем удалите
только пустой каталог `.chimera-test-envs/sqlite.lock` или
`.chimera-test-envs/postgres.lock` и повторите операцию. В Linux используйте
`rmdir`, в PowerShell — `[IO.Directory]::Delete(<полный путь к блокировке>, $false)`.
При несовпадении маркера или обнаружении перенаправленного каталога
проверьте происхождение данных перед любыми ручными действиями.

## Реестр открытых проблем

| ID | Проблема | Граница этапа 02 |
|---|---|---|
| 00-01 | В собранном wheel отсутствует миграция Alembic `0001`. | Стенды запускаются из checkout. Упаковка миграций остаётся открытой. |
| 00-02 | Штатная конфигурация Server допускает SQLite fallback. | Server-стенд использует явный PostgreSQL 16. Общий контракт остаётся этапу 06. |
| 00-03 | Штатный Desktop Local допускает внешний bind через `APP_HOST`. | DEV-стенд слушает `127.0.0.1`. Ограничение штатного входа остаётся этапу 06. |

## Откат

Остановите Flask и при необходимости PostgreSQL командой `stop`. Пока утилита
доступна, можно подтвердить `clean` каждого созданного стенда. Для сохранения
данных остановленного стенда пропустите очистку. Ветка этапа основана на
`main`, миграции приложения и production-конфигурация прежние. До коммита
откатите изменения только в файлах этапа или сохраните рабочую копию и
переключитесь на `main`. Если изменения уже закоммичены, используйте
`git revert <коммит-этапа-02>` в соответствующей ветке.
