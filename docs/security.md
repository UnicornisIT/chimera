# Безопасность и персональные данные

Chimera обрабатывает персональные данные студентов (152-ФЗ). Этот документ
описывает, какие меры реализованы в приложении, а какие остаются за
организацией.

## Учётные записи и вход

- Пароли хранятся хэшами `werkzeug.security` (тот же формат, что в Manticore).
- Минимальная длина пароля — 10 символов, нужны буквы и цифры/символы.
- Начальный администратор и пользователи, созданные администратором, обязаны
  сменить пароль при первом входе.
- Неудачные попытки входа записываются в базу; после `LOGIN_MAX_ATTEMPTS` за
  `LOGIN_WINDOW_SECONDS` вход блокируется (работает между процессами gunicorn).
- Смена пароля завершает остальные сессии пользователя.
- Сессионная cookie: `HttpOnly`, `SameSite=Lax`, `Secure` в режиме сервера.

## Защита веб-интерфейса

- CSRF-токен на всех формах (POST без токена отклоняется).
- Content-Security-Policy без `unsafe-inline`: в шаблонах нет inline-скриптов,
  стилей и обработчиков событий (проверяется тестом).
- `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
  `Referrer-Policy: same-origin`, `Cache-Control: no-store` для страниц.
- Перенаправление после входа — только на относительные адреса.
- Пользовательские шаблоны документов (появятся на этапе документов) будут
  рендериться в `jinja2.sandbox.SandboxedEnvironment`.

## Изоляция организаций

- Все предметные данные принадлежат организации (`organization_id`).
- Фильтр по текущей организации добавляется автоматически ко всем ORM-запросам
  (`chimera/core/tenancy.py`), а запрос к таким данным без выбранной организации
  считается ошибкой. Запись в чужую организацию и перенос записи между
  организациями отклоняются при сохранении.
- Журнал аудита фильтруется по текущей организации явно.
- Для каждого модуля обязателен тест на утечку между организациями.

## Шифрование полей

- Особо чувствительные поля (СНИЛС, паспорт и т. п. — появятся на этапе 2)
  шифруются Fernet (AES-128-CBC + HMAC-SHA256) ключом `DATA_ENCRYPTION_KEY`.
- Для поиска по точному значению хранится «слепой индекс» — HMAC-SHA256 от
  нормализованного значения; по нему нельзя восстановить исходное значение,
  но одинаковые значения дают одинаковый индекс.
- Ротация: `DATA_ENCRYPTION_KEY=НОВЫЙ,СТАРЫЙ` — новые значения шифруются новым
  ключом, старые читаются. Если индекс выводится из ключа шифрования (не задан
  `BLIND_INDEX_KEY`), после ротации индексы нужно пересчитать.

## Журнал аудита

Каждое изменение данных пишется в `audit_log` в той же транзакции: кто, в какой
роли (реальной и действующей), в какой организации, что изменилось (было/стало).
Значения зашифрованных и служебных полей (например, хэш пароля) не
записываются — только факт изменения. Также фиксируются вход, выход, неудачные
попытки, переключение организации, режим «работать как» и операции с бэкапами.

## Резервные копии

- Создаются только системным администратором; файлы получают права `0600`.
- Копия **не шифруется** приложением. Зашифрованные поля внутри неё защищены
  ключом, но остальные данные — нет. Храните копии на защищённом носителе.

## Остаточные риски

- Изоляция организаций реализована в приложении, а не средствами СУБД (нет
  Row-Level Security). Ошибка в коде, обходящая сервисный слой, может её нарушить;
  риск снижается тестами на утечку.
- Связанные данные, загруженные через отношения от «общих» объектов (например,
  все членства пользователя), не фильтруются ORM-фильтром — сервисы обязаны
  запрашивать данные организации явными запросами.
- Системный администратор видит данные всех организаций установки.
- Слепой индекс раскрывает факт совпадения значений у разных записей.
- Защита от перебора паролей привязана к логину и IP; распределённый перебор
  нужно ограничивать на уровне сети.

## Проверка зависимостей

CI запускает `pip-audit` по `requirements-prod.lock` и
`requirements-desktop.lock`, а также `gitleaks` по истории коммитов.
